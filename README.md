# IRR Analysis

`irr-analysis` compares routes currently advertised to a provider with one or
more prefix files generated by `bgpq4`. It reports advertisements that are not
covered by the generated IRR/RPKI filter set.

The tool supports:

- IPv4 and IPv6
- Multiple advertised-route files
- Multiple `bgpq4` filter files
- Junos-style advertised-route output
- IOS XR-style advertised-route output when the AS path follows the prefix
- Mixed IPv4 and IPv6 input in the same run
- Source-aware analysis through the source selection used when invoking `bgpq4`

## Important scope

This tool analyzes the files it is given. It does not query an IRR server or an
RPKI validator itself. If RPKI-derived prefixes should be accepted, include the
`RPKI` pseudo-source when generating the files with an IRRd-backed server.

Example:

```bash
bgpq4 \
  -h whois.radb.net \
  -6 \
  -S RPKI,AFRINIC,ARIN,APNIC,LACNIC,RIPE,RADB \
  -F '%n/%l' \
  AS64496 > as64496-ipv6.txt
```

This preserves the distinction between trusted source selection and the local
analysis. For example, `ALTDB` may be omitted while `RPKI` remains enabled.

## Usage

Both options accept comma-separated file names. Spaces around commas are
ignored.

```bash
irr-analysis \
  --filters as64497-v4.txt,as64497-v6.txt \
  --advertised edge1-pop1-v4.txt,edge1-pop1-v6.txt
```

Short options are also available:

```bash
irr-analysis \
  -f as64497-v4.txt,as64497-v6.txt \
  -a edge1-pop1-v4.txt,edge1-pop1-v6.txt
```

A successful analysis exits with code `0`, even if uncovered routes are found.
Use `--fail-on-uncovered` in automation to exit with code `1` when the report
contains uncovered advertisements:

```bash
irr-analysis \
  -f generated-filter.txt \
  -a advertised-routes.txt \
  --fail-on-uncovered
```

## Accepted filter input

The filter reader scans each nonempty line for its first valid IP prefix. This
supports plain prefix output and common generated configuration formats.
Comments and lines without a prefix are ignored.

Examples:

```text
2001:4:112::/48
2001:288::/32
198.51.100.0/24
```

## Advertised-route parsing

The parser finds the first valid IPv4 or IPv6 prefix on each line instead of
assuming a fixed column. This accommodates status markers such as `*`, `>`,
and platform-specific columns.

Customer ASN extraction is intentionally conservative:

1. The parser first looks for the token `Self`, as seen in Junos output.
2. For a Junos line, the first numeric token after the MED is treated as the
   customer ASN. The displayed AS path remains unchanged, including the MED,
   to preserve compatibility with the original report.
3. Without `Self`, the parser examines tokens after the prefix and ignores
   known status/origin markers. The first plausible ASN after route metadata is
   used as a best-effort IOS XR customer ASN.
4. If no ASN can be identified safely, the route is reported as
   `LOCAL/UNKNOWN` rather than inventing one.

Because command output can vary by Junos/IOS XR release and command form,
validate customer attribution against a few raw lines whenever a new command
format is introduced. Prefix coverage does not depend on successful ASN
attribution.

## Duplicate prefixes

If the same advertised prefix appears in more than one file, the last instance
wins. Route-filter entries are deduplicated. IPv4 routes are compared only with
IPv4 filters, and IPv6 routes only with IPv6 filters.
